# NeoDhizuku

[Dhizuku](https://github.com/iamr0s/Dhizuku)를 기반으로 한 2차 개발 버전으로, 기기 소유자(DeviceOwner) 권한을 다른 앱에 통제된 방식으로 공유합니다.

---

## ⚠️ 미완성 경고

**현재 개발 중인 버전입니다. 일상적으로 사용하는 기기나 운영 환경에서는 사용하지 마세요.**
일부 기능은 막 구현되었고 일부는 실기기 검증이 충분하지 않습니다. 패키지명이 `com.neodhizuku.more`로 변경되어 공식 버전과 **공존할 수 없습니다**(서로 다른 기기 소유자가 됩니다). 먼저 테스트 기기에서 검증하세요. 공식 버전과 데이터 호환이 되지 않으므로 이전 전에 직접 백업하세요.

## 1. 수정 사항 및 새로운 기능

모든 변경 사항은 `NeoDhizuku.UseNeoDhizuku` 마스터 스위치 아래에 있습니다(`app/src/main/java/com/neodhizuku/more/NeoDhizuku.kt`).

> `false`로 설정하면 모든 하위 기능이 비활성화되고 동작이 **완전히 업스트림 원본 구현으로 되돌아갑니다**. 하위 기능을 개별적으로 끌 수도 있어 대조 디버깅에 편리합니다.

### 기본 정보

| 항목 | 업스트림 | 본 프로젝트 |
|---|---|---|
| 패키지명 | `com.rosan.dhizuku` | `com.neodhizuku.more` |
| 앱 이름 | Dhizuku | NeoDhizuku |
| 지원 Android | Android 8.0+ (컴파일 대상 API 37) | 동일 |

> Manifest의 API 권한 이름과 AIDL 패키지명은 **그대로 유지**됩니다. 이는 기존 서드파티 클라이언트가 수정 없이 본 앱을 인식할 수 있도록 하기 위함입니다.

### 보안 강화

- **인증 진입점이 클라이언트가 보고한 UID를 신뢰하지 않습니다**: 서버가 `Binder.getCallingUid()`로 실제 신원을 가져와 일회용 토큰(10분 유효)을 발급합니다. Activity가 검증을 통과한 후에만 해당 UID를 인정합니다. 구버전 클라이언트는 호환 경로를 사용하며 기존 권한을 덮어쓰지 않습니다.
- Provider 인증, `remoteProcess` 명령 감사, 시작 시 자체 서명 검증.
- 서명 허용 목록은 **빌드 시점**에 주입되며, 설정되지 않으면 자동으로 건너뜁니다. 직접 빌드·디버깅하기 편합니다.

### UI 재구성

KernelSU 관리자 앱의 레이아웃 아이디어를 참고하여 Material3로 구현했습니다(**miuix / coui 미사용**):

- **플로팅 하단 내비게이션 바**: 4개 페이지가 공유, 아이콘 + 텍스트, **이모지 미사용**. 비활성화 상태에서는 「홈 / 설정」만 표시. 하위 페이지에서는 바를 숨김.
- **홈 상태 카드**: 활성화 후 「왼쪽 상태 카드 + 오른쪽 위아래 작은 카드 2개」——체크 아이콘 + 활성화됨 + 소유자 유형 + 버전 번호(탭하면 활성화 페이지로), 우측 상단에 인증된 앱 수, 우측 하단에 서비스 실행 시간(`HH:MM:SS`, 서비스 재시작 시 초기화). **비활성화 상태에서는 업스트림 원본 스타일을 유지**합니다.
- **앱 관리**: 탭 없음. Dhizuku 관련 앱은 모두 하나의 목록에 표시되며, 스위치가 인증 상태를 직접 보여줍니다. Manifest에 권한을 선언하지 않았지만 호출을 시도한 앱(일부 설치 프로그램 등)은 자동으로 등록되어 바로 권한을 부여할 수 있습니다.
- **차단 목록 전용 페이지**: 앱 관리에서 분리. 항목별로 차단 해제 가능.
- **인증 다이얼로그**: 진행 표시줄 없음. 「허용」은 연한 녹색, 「거부」는 빨간색으로 강조, 「차단 목록에 추가」는 검은색, 모두 배경 상자 없는 일반 텍스트. 카운트다운은 버튼 행 아래에 작은 글씨로 표시.
- **호출 기록**: 각 앱이 어떤 기능을 호출했는지 기록하며, 모두 짧은 중국어 문장으로 설명합니다. **영구 저장, 기본 30일 보존**. 각 기록에는 당시의 서버 측 실행 로그 조각이 포함됩니다. 별도의 「실행 로그」탭에서 서버 자체 로그를 볼 수 있으며, **비활성화 상태에서도 확인 가능**합니다.
- **서비스 시작/중지**: 우측 상단 버튼은 실행 중에는 X 표시, 중지 후에는 재시작 아이콘으로 바뀝니다. 실행 시간 카드는 중지 시 전체가 빨간색이 되며 「서비스 거부」로 표시됩니다. 중지 후에도 권한 및 호출 기록 조회는 유지되며, 그 외 모든 작업은 거부됩니다.
- **기기 소유자 이전 차단**: 권한을 얻은 서드파티 앱은 `binderWrapper`를 통해 기기 소유자로서 DPM의 임의 메서드를 호출할 수 있습니다. 반환 수단을 제공하지 않으면 이전 후 소유자를 되찾을 수 없습니다. 설정 항목 「서드파티 앱의 기기 소유자 이전 허용」은 **기본적으로 꺼져 있으며**, 꺼진 상태에서는 직접 거부하고 알림을 표시합니다.
- **서비스 정책 페이지**: 설정 내부의 2단계 메뉴. API 서비스 마스터 스위치, 허용 목록 모드, 서비스 중지 후 처리 방식, 기기 소유자 이전 스위치를 한곳에서 관리합니다.
- **계정 삭제 없는 임시 활성화**: 업스트림의 「먼저 모든 계정을 삭제해야 한다」는 요구 사항을 없앴습니다. 아래 전용 섹션을 참고하세요.
- **테마 페이지**: 다크 모드 4단계(시스템 따르기 / 라이트 / 다크 / 다크 순수 블랙 AMOLED) + 동적 색상 추출 스위치. 다크 모드는 접이식 선택기 사용.
- **설정 페이지**: 「관리」섹션 항목 추가, **비활성화 시 섹션 전체 숨김**.
- **활성화 오류 안내**: 영어 원본 오류를 중국어 원인 + 처리 제안 + 복사 가능한 진단 정보로 매핑합니다.

### 디버그 로그

TAG는 `NeoDhizuku`로 통일되어 있으며 분류 하위 태그(`Nav` / `Theme` / `Perm` / `Home` / `Apps` / `Daemon` / `Server` / `Activate` / `UI` / `Boot`)를 가집니다. 스위치는 `NeoDhizuku.DebugLog`. 꺼진 경우 완전히 무음이며 문자열 결합 비용도 없습니다.

```bash
adb logcat -s NeoDhizuku:V              # 전체
adb logcat -s NeoDhizuku:V | grep Nav   # 내비게이션만
```

## 2. 참고 사항 및 사용법

### 활성화

업스트림과 동일하게 Shizuku, ADB, 계정 삭제 불필요 모드로 기기 소유자가 될 수 있습니다.
**업스트림 안내에 주의하세요: 계정이 없는 기기에서 설정할 것을 권장합니다.** 이미 계정이 있다면 먼저 제거해야 할 수 있습니다.

기기 소유자가 된 후, 서드파티 앱은 Dhizuku API를 통해 기기 소유자 권한 사용을 신청할 수 있습니다.

### 계정 삭제 없는 임시 활성화

업스트림은 **계정이 전혀 없는 상태**에서의 설정을 권장하며, 그렇지 않으면 먼저 제거해야 합니다. 본 방식은 이 제한을 우회합니다.

**원리**: `DevicePolicyManagerService`에서 계정 검사 `hasIncompatibleAccountsOrNonAdb`는 `isAdb` 분기 안에서만 읽힙니다. 원본은 ADB(`dpm set-device-owner`)를 거치므로 `isAdb=true`이고 세 개의 관문이 모두 평가됩니다. 본 방식은 **앱 자체 uid**로 직접 호출하므로 `isAdb=false`가 되어 `hasUserSetupCompleted`만 검사되고, **계정은 전혀 읽지 않습니다**.

**7단계**:

| 단계 | 실행자 | 내용 |
|---|---|---|
| ① | shell | `cmd role set-bypassing-role-qualification true` |
| ② | shell | `cmd role add-role-holder --user 0 android.app.role.DEVICE_POLICY_MANAGEMENT <pkg>` |
| ③ | shell | `settings put secure user_setup_complete 0` |
| ④ | 앱 자체 | 리플렉션으로 `forceUpdateUserSetupComplete(0)` 호출, ③의 값을 DPM 메모리 상태로 반영 |
| ⑤ | 앱 자체 | 리플렉션으로 `setActiveAdmin` |
| ⑥ | 앱 자체 | 리플렉션으로 `setDeviceOwner` |
| ⑦ | shell | `settings put secure user_setup_complete 1` |

③과 ④는 **반드시 쌍으로** 수행해야 합니다. ③만 하면 효과가 없고 메모리 상태가 바뀌지 않아 관문이 닫힌 상태로 남습니다. ④의 매개변수는 상태값이 아닌 userId이며, Settings의 실제 값을 메모리로 양방향 복사합니다. 따라서 ③은 생략할 수 없습니다.

**세 가지 전제 조건**:

- Shizuku 또는 root 권한(①③⑦의 shell 명령 실행에 필요. 일반 앱은 `WRITE_SECURE_SETTINGS`를 얻을 수 없습니다)
- Android 13(API 33) 이상(`DEVICE_POLICY_MANAGEMENT` 역할은 이 버전에서 도입되었습니다)
- 아직 기기 소유자가 아닌 상태

**부작용**: 값이 0인 동안 3버튼 내비게이션의 홈 및 최근 앱 키가 작동하지 않습니다(뒤로 키는 작동, 제스처 내비게이션은 영향 없음). 코드는 `finally`에서 반드시 복원하므로 기기가 「설정 미완료」상태로 남지 않습니다.

**문제 해결**: 역할 명령이 `RC=0`을 반환해도 권한이 여전히 DENIED라면, 대개 Manifest에 `MANAGE_DEVICE_ADMINS` / `MANAGE_PROFILE_AND_DEVICE_OWNERS`가 선언되지 않은 것이 원인입니다. 이 둘은 signature 수준 권한이므로, 선언되어 있지 않으면 시스템이 역할 부여 시 함께 허용하지 않습니다. 페이지에 이 안내가 직접 표시됩니다.

설정 마법사가 복원되지 않은 경우, 페이지는 빨간색 안내를 표시하고 처음 두 단계를 비활성화하여 「수동 복원」만 남깁니다.

### 권한 관리

- 서드파티 앱의 첫 호출 시 인증 요청이 표시되며, 허용·거부·차단 목록 추가를 선택할 수 있습니다.
- **차단 목록에 추가되면 해당 앱의 인증 요청은 더 이상 처리되지 않습니다.**
- 「앱 관리」에서 언제든 각 앱의 권한을 켜고 끌 수 있습니다. 「차단 목록」페이지에서 차단을 해제할 수 있습니다.
- **허용 목록 모드**를 켜면 허용 목록에 있는 앱만 고위험 인터페이스를 호출할 수 있습니다.

### 스위치 사용법

`NeoDhizuku.kt`를 편집합니다:

```kotlin
const val UseNeoDhizuku: Boolean = true   // 마스터 스위치, false = 모두 업스트림 동작으로 되돌림
const val UseThemePage: Boolean = true    // 하위 기능: 테마 페이지
const val DebugLog: Boolean = true        // 하위 기능: 디버그 로그
```

문제 진단 팁: 먼저 `UseNeoDhizuku = false`로 기준 버전을 빌드하고 `true`로 바꿔 비교하세요. 특정 하위 기능에 문제가 있으면 그것만 따로 꺼서 위치를 특정합니다.

### 서비스 정책

설정 → 「서비스 정책」, 세 개 섹션:

**① API 서비스**: 마스터 스위치(다른 앱의 API 서비스 사용 허용), 허용 목록 모드(허용 목록의 앱만 API 서비스 사용 허용).

**② 서비스 중지 후 처리 방식**(접이식 선택기, 서비스가 중지된 후에만 적용):

| 옵션 | 동작 |
|---|---|
| 위험한 서비스 거부 후 실패 반환 | 서비스는 조회 가능, 읽기 전용이 아닌 작업은 모두 거부 |
| 위험한 서비스 거부 후 성공 반환 | 통과시키지만 실제로 실행하지 않고 성공만 반환 |
| 서비스 완전 거부 후 실패 반환 | null 반환, 다른 앱이 서비스를 찾을 수 없음 |
| 서비스 완전 거부 후 성공 반환 | 빈 결과 반환 |
| 아무것도 하지 않음 | 인증 요청을 대기 상태로 두고 클라이언트는 무한정 대기 |

「아무것도 하지 않음」은 스레드를 막는 대신 **콜백을 호출하지 않는** 방식으로 구현되어, 다른 호출 처리에는 영향을 주지 않습니다.

**③ 기기 소유자 이전**: 앞서 「기기 소유자 이전 차단」에서 설명한 스위치입니다.

### 알려진 제한

- 플로팅 하단 바는 좌우 스와이프로 페이지를 전환하는 Pager 구조가 아니며, 탭으로만 전환할 수 있습니다.
- 테마는 Material3 네이티브 `dynamicColorScheme`(Android 12+ 시스템 지원)을 사용하며, 서드파티 팔레트 라이브러리를 도입하지 않았습니다.
- **공식 Dhizuku와 공존할 때**: 공식 패키지 authority를 하드코딩한 클라이언트(amarok, 爱玩机工具箱 등)는 본 앱이 아니라 공식 버전에 연결되어, 「공식 버전 다이얼로그가 뜨고 본 앱이 응답하지 않는」현상이 발생합니다. ContentProvider authority는 전역적으로 고유하여 탈취할 수 없으므로, 해결책은 공식 버전을 제거하고 `neoCompat` 또는 `official` 플레이버로 전환하는 것입니다.
- **계정 삭제 없는 활성화는 Android 13+만 지원**합니다. 그보다 낮은 버전에서는 페이지에 「지원되지 않음」이 표시되고 단계가 숨겨집니다.
- Shizuku API 14에서 `newProcess`가 제거됩니다. 그 시점에 이 활성화 경로의 shell 실행은 User Service로 이전해야 합니다.

## 3. 빌드 방법

### 환경 요구 사항

Android Studio **Quail 4(2026.1.4)** 이상(AGP 9.4.1의 최소 요구 사항), JDK 21.
SDK Manager에서 SDK Platform 37, Build Tools 37.0.0, NDK 29.0.14206865를 설치해야 합니다.

### 빌드

프로젝트에는 세 가지 플레이버(product flavor)가 있습니다. `namespace`와 소스 패키지명은 `com.neodhizuku.more`로 고정되어 있고,
`applicationId`와 provider authorities만 플레이버에 따라 달라집니다:

| 플레이버 | applicationId | 공식 authority 등록 | 공식 Dhizuku와 공존 | 공식 패키지를 하드코딩한 클라이언트 호환 |
|---|---|---|---|---|
| `neo` | `com.neodhizuku.more` | 아니오 | **가능** | 아니오 |
| `neoCompat` | `com.neodhizuku.more` | 예 | 불가 | **예** |
| `official` | `com.rosan.dhizuku` | — 그 자체가 공식 | 불가(동일 패키지) | **예** |

`neo`와 `neoCompat`은 applicationId가 같아 동시에 설치할 수 없지만, 비교 테스트용으로 각각 빌드해 둘 수 있습니다.

```
./gradlew assembleNeoDebug        공존版(일상 사용 권장)
./gradlew assembleNeoCompatDebug  인계版(먼저 공식 Dhizuku 제거 필요)
./gradlew assembleOfficialDebug   공식 패키지版(먼저 공식 Dhizuku 제거 필요)

./gradlew assembleBothDebug       neo + neoCompat 두 개를 한 번에 빌드
./gradlew assembleAllDebug        세 개를 한 번에 빌드
```

릴리스版은 `Debug`를 `Release`로 바꾸세요(세 개를 한 번에 빌드하는 `assembleAllRelease`도 있습니다).

> **중요**: 기기 소유자는 동시에 하나의 패키지에만 속할 수 있습니다. `neoCompat` / `official`은 모두
> **먼저 공식 Dhizuku를 제거**해야 합니다. 그렇지 않으면 provider authority가 충돌하여
> 설치에 실패합니다(`INSTALL_FAILED_CONFLICTING_PROVIDER`). 설치 후 다시 활성화해야 합니다.

저장소 기본값은 디버그 서명(`keystore/`)입니다. 배포 전에 반드시 자신의 서명 설정으로 교체하세요.

## 4. 향후 계획(완료 및 테스트 후 Release 버전을 정식 공개합니다)

- [-] **인증 진입점 개편**: 모든 서드파티 앱이 안정적으로 인증 요청을 시작할 수 있도록 합니다. 현재 일부 클라이언트(주로 구버전 API에 의존하는)는 다이얼로그도 띄우지 않고 요청도 보내지 않습니다. 시도한 서버 측 인계 방식은 실측에서 효과가 없었으므로, 실제 실패 지점(클라이언트가 `requestPermission`을 호출하는지, listener가 콜백을 받는지, 알림이 실제로 발송되는지)을 먼저 파악한 뒤 재설계해야 합니다.
- [√] ~~계정 삭제 없는 기기 소유자 활성화~~ —— 구현 완료(「계정 삭제 없는 임시 활성화」참조)
- [-] 인증 진입점의 「UID 자기 보고」가 실제로 악용 가능한지 데모로 실측(정적으로는 공격 표면이 존재, 실제 영향은 미확인).
- [-] 인증 다이얼로그에 권한 범위 표시.
- [-] 위임 범위(delegated scopes) 설정 항목 —— API는 지원하지만 UI에 진입점이 없음.
